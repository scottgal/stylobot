# Performance pass — fast path and high-load surface

Date: 2026-05-31. Source data: 1-hour soak on the win-x64 AOT gateway at
50 RPS target (38.6 actual) with detection ON via API key, async Kestrel
upstream. 150,669 requests, 1.25% errors (mostly EOFs in the first 5s
warm-up), `p50 = 11 ms, p95 = 15.5 ms, p99 = 71 ms`. Memory plateaued in
the 150–220 MB band with regular GC reclaim; SQLite grew linearly at
~290 B/req (sessions.db only).

## Where is the latency actually going?

The 49 documented detectors are blindingly fast in isolation. Summing the
benchmark table from `CLAUDE.md`:

| Phase | Cost (ns) |
|---|---|
| Intent (Navigation) | 2,341 |
| Heuristic (Bot) | 4,255 |
| UserAgent (Chrome) | 2,058 |
| Behavioral (Normal) | 1,446 |
| CacheBehavior | 1,335 |
| Ip (Datacenter) | 537 |
| Header (Bot/curl) | 507 |
| MultiLayerCorrelation | 330 |
| FastPathReputation | 308 |
| Inconsistency | 135 |
| HeaderCorrelation | 50 |
| **Total** | **13,302 ns ≈ 13 µs** |

Observed p50 under steady load: **11,000 µs**. So **~99.9 % of fast-path
time is not in the documented detector code**. It is in:

1. Foundation contributors not in the benchmark suite (`Signature`,
   `TransportProtocol`, `PiiQueryString`, `IdentityVector`,
   `FingerprintPrior`, `FastPathReputation`, `ContentSequence`,
   `FingerprintMatch`).
2. Orchestrator overhead: wave dispatch, contribution merging, signal
   sink writes.
3. Middleware: signature compute, verdict-gate decision, action policy
   execution, `HttpContext.Items` writes.
4. YARP proxy: HTTP-client lookup, request forwarding, response copy.
5. Network: Mac → WiFi → Win box, plus loopback gateway → upstream.

The detector benchmarks are measuring the *cheap* parts. The next round
of detector benchmarks should cover foundation contributors and the
orchestrator's dispatch + merge path.

## High-impact targets in the hot path

### 1. Per-request heap allocations

Grep across `BotDetectionMiddleware` + `BlackboardOrchestrator` finds
**20+ `new Dictionary<string, object>` / `new HashSet<string>` per
request**. Even on the verdict-cache fast-path
(`BotDetectionMiddleware.cs:388`) we still allocate a fresh dictionary
just to seed `PrimarySignature`. At 50 RPS that is 1000+ dict allocs/s.
Under 500 RPS, 10 000+ alloc/s — every one a Gen 0 collection driver.

Fixes, in order of effort:

- **Verdict-cache fast-path: stop allocating the seed dict.** Write the
  signature directly into `HttpContext.Items` and skip the
  `AggregatedEvidence.Signals = new Dictionary<>(...)` construction.
  Cached evidence's Signals can be an `ImmutableDictionary<string,
  object>.Empty` singleton.
- **Pool the per-request signal dictionaries.** Add a per-thread
  `DictionaryPool<string, object>` that hands out a preinitialised
  `StringComparer.OrdinalIgnoreCase` dict; return on request end. Avoids
  ~5 dict allocs per detection.
- **Merge contributions into a single growable list** (`ArrayPool<T>`-backed),
  instead of `new List<DetectionReason>(contributions.Count)` per
  request (line 2342).

### 2. Locks that serialize per-signature work

`SignatureCoordinator` uses `private readonly SemaphoreSlim _lock = new(1, 1)`
(`SignatureCoordinator.cs:897`) — a hard 1-permit mutex. If this is
contended on the request hot path, all requests for a single signature
serialize. At low RPS or with many distinct signatures, this is
invisible; at 200+ RPS for a small set of signatures (the realistic
case under attack), it caps the per-signature processing rate.

Fixes:

- Replace with **striped locking** (256-bucket array of `SemaphoreSlim`
  keyed by `signature.GetHashCode() & 255`). Same exclusion guarantees
  per logical key, no global serialisation.
- For the read-mostly metric updates inside the semaphore, swap to
  `Interlocked.Increment` on packed `long` counters and skip the
  semaphore entirely on those paths.

`BlackboardOrchestrator` has several `lock(_lock)` for state read/write
(lines 1516, 1525, 1550, 1563, 1579). At ms-scale these are fine, but
under high load the `_failureCount` reads in particular are read often
and could be `Interlocked.Read`.

### 3. Lazy `IdentityVector` build for verdict-cache hits

`IdentityVectorContributor` (Priority 5) builds a 129-dim float vector
from the request: 100 Markov-transition slots + 10 stationary + 8
temporal + 8 fingerprint + 3 timing. That's a meaningful allocation
even before any compute — a `new float[129]` per request is 516 B + GC
pressure. The matcher then re-uses this vector.

But on a **verdict-cache hit** the matcher doesn't run and the score is
already decided — so the vector is computed and immediately thrown
away. At hit rates north of 70 % (typical for a busy site with few
distinct signatures), most of this work is wasted.

Fix: short-circuit `IdentityVectorContributor.ContributeAsync` when
`state.HasSignal(SignalKeys.VerdictCacheHit)` is already true (the
verdict gate would need to write this). One signal check, skip the
vector build.

### 4. Pool the `float[129]` identity vectors

Even when the vector IS needed, it's a fresh `new float[129]` per
request. Use `ArrayPool<float>.Shared.Rent(129)` + `Return(...)` in a
`finally`. Caveat: any code that hangs onto a vector reference past
request end (e.g. session snapshots) must copy first.

### 5. Pre-compute the primary signature once per request

`ComputeSignature(context)` is invoked twice in the middleware (lines
250 for signature-only paths, 362 for the verdict-gate path). The
result is cached on `HttpContext.Items[PrimarySignature]` after the
second call, but the first call isn't shared. Hoist the compute to the
very top of the middleware and stash it once; both code paths read it
back.

### 6. YARP `HttpMessageHandler` pooling

The Console's `Program.cs` only sets `listenOptions.Protocols =
Http1AndHttp2` for the gateway-side. YARP's `HttpMessageHandler` to the
upstream uses default `SocketsHttpHandler` limits, which on .NET 10 means
`MaxConnectionsPerServer = int.MaxValue` but `PooledConnectionLifetime
= Timeout.InfiniteTimeSpan` and `PooledConnectionIdleTimeout = 2 min`.

For long-running gateways serving many distinct upstreams, tune:

```csharp
yarp.Services.AddSingleton<IForwarderHttpClientFactory, ...>();
// or via ClusterConfig.HttpClient:
HttpClientConfig {
  EnableMultipleHttp2Connections = true,
  RequestHeaderEncoding = "Latin1",
}
```

Plus a custom `SocketsHttpHandler` with `PooledConnectionLifetime = 5
min` so DNS changes are picked up under churn.

### 7. Kestrel limits are all defaults

`Program.cs:724` only sets `listenOptions.Protocols`. Everything else
is default. For a gateway expected to absorb load spikes, set explicit
limits so the failure mode is **fast refusal** rather than queue-and-
timeout:

```csharp
builder.Services.Configure<KestrelServerOptions>(opts => {
    opts.Limits.MaxConcurrentConnections          = 10_000;
    opts.Limits.MaxConcurrentUpgradedConnections  = 1_000;
    opts.Limits.MaxRequestBodySize                = 256 * 1024;   // tighten -- we proxy GETs mostly
    opts.Limits.KeepAliveTimeout                  = TimeSpan.FromSeconds(30);
    opts.Limits.RequestHeadersTimeout             = TimeSpan.FromSeconds(10);
    opts.Limits.MinRequestBodyDataRate            = new MinDataRate(100, TimeSpan.FromSeconds(10));  // relaxed (was default 240/5s) -- still slowloris-safe, kinder to slow mobile uploads
    opts.Limits.MinResponseDataRate               = new MinDataRate(100, TimeSpan.FromSeconds(10));
    opts.Limits.Http2.MaxStreamsPerConnection     = 200;           // up from 100 default
    opts.Limits.Http2.InitialConnectionWindowSize = 1024 * 1024;   // 1 MB up from 64 KB
});

// Pre-warm the ThreadPool so the first burst doesn't pay thread-creation latency
ThreadPool.SetMinThreads(workerThreads: 200, completionPortThreads: 200);
```

Without `SetMinThreads`, the first 200 concurrent requests are racing
ThreadPool growth. The 252 "unexpected EOF" errors we saw in the first
5 s of the soak match this signature exactly (cold thread pool, slow
ramp).

## Load-shedding playbook

Things stylobot can do TODAY when load spikes — none currently
implemented:

1. **Drop wave-0-only mode**: when `Kestrel.Connections > N`, the
   orchestrator stops running classifier waves and emits only foundation
   signals + the cached prior. Fast verdict, no learning. Recovers when
   load drops.
2. **Refuse new TCP connections** at the Kestrel level above a
   high-water-mark (set `MaxConcurrentConnections`). The OS rejects with
   TCP RST; clients back off naturally instead of queueing on Kestrel.
3. **Refuse unknown signatures** when load > threshold: a new visitor
   gets HTTP 503 with `Retry-After: 5` until the burst clears. Returning
   visitors hit the verdict cache and proceed normally.
4. **Shed slow-path coordinator** (the matcher Pass 2 already mentions
   "shed under pressure" in code comments but no shedder is wired). Make
   `FingerprintMatchContributor.RunPass2InternalAsync` skippable when an
   in-flight gauge exceeds a threshold; fall back to L1-only matching.

The HTTP/2 multiplexing settings above also help — fewer TCP connections
but more parallel streams over each.

## Quick recommendations summary

| Change | Effort | Estimated impact |
|---|---|---|
| Stop allocating Dictionary on verdict-cache hit | S | -3 ms p50 on hot path |
| Pool `float[129]` identity vectors | S | -5 % GC pressure |
| Hoist `ComputeSignature` to once per request | S | -50 µs (signature compute) |
| Striped locking on `SignatureCoordinator._lock` | M | unlocks 4-8x scaling at 200+ RPS |
| Skip `IdentityVector` build on verdict-cache hits | M | -1-2 ms p50 |
| Explicit Kestrel limits + `SetMinThreads` | S | kills cold-start EOF errors |
| YARP HttpClient pool tuning | S | -1 ms p50 |
| Load-shed mode in orchestrator | L | sustains 5-10x current peak RPS |

## What this won't change

- The session.db growth rate (~290 B/req). That's the cost of recording
  one row per request. Already linear and bounded; not a perf concern.
- The 16-min "gap" seen mid-soak — that was a network-side artifact
  (Mac↔Win over WiFi, k6 keep-alive pool getting stuck). Not a gateway
  problem.
- The 11 ms ↔ 15 ms p50→p95 gap. Some of that is genuinely the LAN RTT
  + Kestrel processing tail. Improving it would require either a
  shorter physical path or HTTP/2 multiplexing.
